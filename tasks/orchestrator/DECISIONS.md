## D1 · CLI 退出码契约（G1+G7，已闭环）

`0` = 成功（**含 hook 运行时恒 0**——"deny 是正常决策"不是错误）；`1` = 操作失败（doctor FAIL、install 中止/回滚、卸载拒绝、bootstrap 失败）；`2` = 用法错误（未知子命令/未知 agent）。**后续任何切片不得回归此契约。**

## D2 · doctor 新鲜度用 WARN，不用 FAIL（G2，已闭环）

"脚本陈旧"与"用户有意定制"在外部不可区分 → 一律 **WARN，不改退出码**。`--json` 暴露 `warn`/`exitCode` 供严格 CI 自行升级。**理由**：把两者混为 FAIL 会逼用户删除自定义规则，可用性反噬安全性。

## D3 · 脱敏的过度与轮转（G15，已闭环）

- 密钥轮转用 `Move-Item -Force`（覆盖旧 .1）**可接受** —— 目标是不留明文，不是保留审计历史。
- ≥40 字符长串的过度脱敏**可接受** —— 继承自 core 单源，修也应在 core 层修，不在 ps1 层特判。
- 历史明文日志清理**不是切片验收项**（且当时证据是 A/B 测试污染，非真实泄漏）。

## D5 · 编排流程纪律（Round 25–43 沉淀）

3. **任务卡中的事实性数字应标"以实测为准"**。三次派活中两次由实现者纠正编排者的计数错误（core 模式 9→10、sh 副本 4→3）。
4. **A/B 对照脚本必须隔离 TEMP**（曾污染生产日志、制造假泄漏证据）。
5. **ps1 hook 读进程 stdin**，同进程管道探测会得假阳性"全 deny"。

## D8 · 判定"新回归"必须先**重建基线对照**，不得只凭期望值（Round 199-200）

**背景**：对 G15b-FIX 的复验中，某轮 Evaluator 把 `docker run --name mysql -p3306:3306 mysql` 被脱敏标为 `OK=False`（期望 keep），看似"FIX 引入的过度脱敏"。而改派的新 Evaluator **重建 G15b 基线逐条对照**后得出：
- `-p 3306:3306`（带空格）：**两版都不脱敏** → 与 FIX 无关
- `-p3306:3306`（无空格）：**两版都脱敏** → **既有行为**（G15b 的 `-p` 规则本就要求值含非数字，`:` 满足）

即：**该"回归"在基线里早就存在，不是本次修复引入的**。

**固化为纪律**：
1. 报"新回归"前，必须**用基线版本（`git show <commit>:<path>` 或历史副本）跑同一载荷**，给出 before/after 并列输出；
2. 判定分三类，不得混为一谈：**新引入**（基线无、现值有）/ **既有未修**（两版都有）/ **已修复**（基线有、现值无）；
3. 只有第 1 类才是"本次修复的回归"；第 2 类应记为**新发现的既有缺口**并另行排期，**不构成对本次修复的 REJECT 依据**（除非任务卡明确要求一并修）。

**同源**：与 D6（攻击面选错）、D7（邻居面选错）并列——**这是"对照面"选错的第三种形态**。

## D7 · "不得误伤"的验收标准必须由**构造邻居**产生（Round 181 教训）

**背景**：G15b-FIX 用手法 F4「命令上下文限定」修 `-p<全数字>` 泄漏，却引入了**过度脱敏回归**——独立 Evaluator 构造的邻居载荷命中：
- `docker run --name mysql -p 3306:3306 mysql` → **容器名 `mysql` 触发上下文规则**，端口映射被误脱敏
- `npm install --user …` / `chown user:group` / `MYSQL_ROOT_PASSWORD` 同样被误伤

**根因（任务卡层面的缺陷）**：我在 `FIX_BRIEF_G15b` 里写"不得误伤既有 no-fp 用例"，并**列举了三条已知用例**（`ssh -p2222`/`docker run -p 8080:80`/`npm run build --prefix`）。这只防住了**已知**用例，**防不住新规则的邻居**。

**固化为纪律**：凡"新增/修改匹配规则"的任务卡，"不得误伤"条款**不得只列已知用例**，必须要求实现者**为新规则构造 N 条邻居载荷**（同前缀、同参数位、但语义无关的合法命令），并把这些邻居**钉进回归测试**。评价标准：**新规则必须能区分"我要拦的形态"与"它的邻居"**。

**同源观察**：这与 D6 第 1 条（"变异必须攻击生产路径而非被测函数"）是同一类错误的两个面——**攻击面/邻居面选错，测试就会给出虚假信心**。

## D6 · G15b 被独立验收 **REJECT**（Round 121）——本会话最重要的方法学案例

**结论**：`EVALUATION_RESULT_G15b.md` 裁决 REJECT。已发 `FIX_BRIEF_G15b.md` 进入 FIX 循环。

**决定性缺陷 D1（P0）**：sh 端新增的 13 条 `redact_text()` **只有测试入口 `--redact-stdin` 调用**；生产出口 `deny_command`→`redact_cmd()` **一行未改**（仍是旧 2 条 sed）。→ 四类残留密钥在 sh 的**真实 deny 输出**里**全部明文泄漏**，ps1 端则全部正确。

**D2（P0）**：parity 闸门**恒绿且守错对象**——它只比对测试入口，对"生产路径完全失效"零告警。Evaluator 的 M2 变异（只把 `redact_cmd` 改直通）→ **闸门仍绿**。

**D3（P1）**：生产路径残留 GNU-only `sed I` 标志（BSD/macOS 静默失效）。
**D4（P1）**：`-p<全数字>` / `--user u:p` **两端**明文泄漏。

**为什么实现者没发现（三条教训，已固化为纪律）**
1. **变异验证必须攻击"生产路径"，不能只攻击被测函数**。实现者 3/3 CAUGHT 全绿，但攻击面是 `redact_text`（生产永不调用）→ 结论无意义。**"测试变红"不等于"闸门有效"，要问"它守的是谁"。**
2. **报告与代码可能不符，且实现者未必自知**：报告 §5 声称 `redact_cmd` 已改为 `tr → redact_text → JSON 转义`；实测该集成**从未发生**。→ 验收必须**读代码体**，不能只读报告与测试结果。
3. **新增能力的"接线"是独立于"能力本身"的失败点**：13 条规则写对了、单测过了、跨端 parity 绿了——**但它没接到生产出口**。今后凡"新增函数/规则"，验收必查**调用链是否真的走到它**（与 G2 的"核对调用链实际路径"同源，那次是审计读错实现，这次是生产未接线）。

**编排者裁量（与 Evaluator 分歧）**
- **A1 `ssh -i <路径>`：不认定为泄漏、不脱敏**。`-i` 是私钥**文件路径**而非密钥值；脱敏它属过度脱敏，与既有"过度脱敏不接受"原则冲突。→ 已写入修复卡要求记录该分歧。
- **A2 `-P<v>`（mysql 大写 P 实为 port）**：低优先，仅在零误伤成本下做。
